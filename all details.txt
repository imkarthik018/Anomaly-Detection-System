ANOMALY DETECTION PROJECT - COMPLETE EXPLANATION FOR SEMINAR AND PROJECT REVIEW

Project Name:
Anomaly-Detection-main

Project Objective:
This project detects suspicious or unusual login behavior from user activity data. It supports:
1) Batch anomaly detection on uploaded CSV login datasets.
2) Real-time anomaly scoring for live login attempts.
3) Live SOC-style threat monitoring dashboard.

==================================================
1. HIGH-LEVEL OVERVIEW
==================================================

This repository contains multiple implementations, but the main active system is a Flask web application in:
WebFrontend/

The active application:
- Accepts login datasets and detects anomalies.
- Scores each live login attempt in real time.
- Shows threat trends and event streams on a dashboard.
- Stores anomalous events in a database.
- Optionally sends alert emails when anomalies are found.

There are also older/secondary components:
- Backend/machine.py: standalone CLI anomaly pipeline (offline script).
- Frontend&Database/fontend_database.py: old Streamlit version (marked deprecated in code).

5. CORE ANOMALY DETECTION LOGIC (IMPORTANT FOR SEMINAR)
==================================================

The project uses Isolation Forest, an unsupervised anomaly detection algorithm.

Why Isolation Forest?
- It isolates outliers quickly using random partitioning.
- Good for unsupervised data where labels are unavailable.
- Widely used for fraud/anomaly detection use cases.

----------------------------------
5A) Batch Detection (WebFrontend/anomaly_core.py)
----------------------------------

Primary function:
- process_csv(file_like)

Flow:
1) Read uploaded CSV with pandas.
2) Validate required columns:
   - activity_type
   - location
   - ip_address
3) Filter only login rows:
   activity_type == "login" (case-insensitive)
4) Encode categorical fields:
   - location -> location_encoded (LabelEncoder)
   - ip_address -> ip_encoded (LabelEncoder)
5) Build feature matrix:
   X = [location_encoded, ip_encoded]
6) Train + score model:
   IsolationForest(contamination=0.01, random_state=42)
7) Predict anomaly labels:
   model output -1 => anomaly_flag = 1
   model output  1 => anomaly_flag = 0
8) Get anomaly score:
   decision_function(X) -> anomaly_score
   (Lower score means more anomalous)
9) Build output for UI:
   - anomaly counts
   - table rows
   - chart payload (if timestamps available)
10) If anomalies exist:
   - persist to database
   - optionally send email alert

Key seminar point:
- Batch model currently uses only two encoded features (location + IP).
- timestamp is mainly used for visualization, not model training.

----------------------------------
5B) Realtime Detection (WebFrontend/realtime_detector.py)
----------------------------------

Class:
- RealtimeThreatEngine

Training/Fit:
- fit_from_csv(sample_login_events.csv)
- Reads baseline login events.
- Builds token maps for categories:
  - location token dictionary
  - IP token dictionary
- Fits model:
  IsolationForest(contamination=0.01, random_state=42, n_estimators=200)

Realtime inference:
- score(location, ip_address, user_id, source)
- Converts location/IP into numeric tokens.
- Runs model predict + decision_function.
- Creates enriched threat event object with:
  - anomaly_flag
  - anomaly_score
  - threat_level
  - risk_score
  - metadata (timestamp, user, source, etc.)

Threat level mapping:
- NORMAL   -> non-anomaly
- ELEVATED -> anomaly with weaker anomaly score
- HIGH     -> anomaly with score < 0
- CRITICAL -> anomaly with score < -0.02

Risk score:
- Derived heuristic, clamped 0-100.
- Strong anomalies produce high risk values.

6. END-TO-END DATA FLOW (WHAT HAPPENS IN DEMO)
==================================================

A) Batch analysis flow:
1) User uploads CSV on "/".
2) app.py sends file stream to process_csv().
3) Model detects anomalous login rows.
4) results.html displays:
   - total logins
   - anomalies detected
   - anomaly table with highlights
   - chart of anomaly severities
5) anomalies are saved to DB and can trigger email.

B) Realtime login flow:
1) User enters login info in "/login".
2) Frontend calls POST /api/login.
3) Server extracts client IP + provided location.
4) RealtimeThreatEngine scores event instantly.
5) Response returns threat level + risk + score.
6) Event is pushed to dashboard via Socket.IO.
7) If anomaly, event can be stored and alert emailed.

C) Live monitor flow:
1) Open "/live" dashboard.
2) Receives streaming events using Socket.IO:
   - threat_event
   - stats_update
3) Shows counters, recent events, and trend chart.
4) Supports API ingestion and synthetic demo stream.

7. DATABASE AND ALERTING
==================================================

Database:
- Table name: login_anomalies
- Default: SQLite file login_anomalies.db
- Can switch DB using DATABASE_URL (e.g., PostgreSQL).

Email alerts:
- Triggered when anomalies are found.
- Uses SMTP (Gmail style configuration).
- Includes anomaly details in email body/attachment.
- Can be disabled by env:
  SKIP_EMAIL=1
- Realtime alerts also use cooldown:
  LIVE_EMAIL_COOLDOWN_SEC (default ~120s) to avoid spam.

11. STRENGTHS, LIMITATIONS, AND IMPROVEMENT IDEAS
==================================================

Strengths:
- End-to-end working pipeline (upload -> detect -> visualize -> persist -> alert).
- Supports both batch and realtime anomaly detection.
- Clear web UI for demonstration and project review.
- Easy deployment for local demo (Flask + SQLite).

Current limitations:
- Active web model uses only location/IP encoded integers (limited feature richness).
- Fixed contamination may not fit all datasets.
- Label encoding can impose artificial ordering on categories.
- Baseline model quality depends heavily on sample login data quality.
- No supervised ground-truth evaluation metrics in main web flow.

Suggested improvements:
- Add engineered temporal and behavioral features:
  login hour, weekday, user frequency, IP novelty score, geo distance.
- Use OneHotEncoder or target-independent embedding techniques.
- Introduce configurable contamination and threshold tuning in UI/admin config.
- Add model evaluation metrics and confusion-matrix workflow (if labels available).
- Add model retraining schedule and concept-drift monitoring.
- Add authentication and role-based admin access for production hardening.

13. QUICK Q&A PREPARATION (FOR REVIEW PANEL)
==================================================

Q1) Which algorithm is used?
Ans: Isolation Forest (unsupervised anomaly detection).

Q2) Why unsupervised?
Ans: Real anomaly labels are usually scarce; unsupervised method can detect outliers directly from patterns.

Q3) What are main features now?
Ans: Location and IP address encoded numerically in active Flask model.

Q4) How is anomaly interpreted?
Ans: anomaly_flag=1 from model prediction (-1), and lower decision score means stronger anomaly.

Q5) Does project support realtime?
Ans: Yes, via RealtimeThreatEngine + Flask-SocketIO event streaming.

Q6) Where are anomalies stored?
Ans: SQL table login_anomalies (SQLite by default, PostgreSQL possible).

Q7) Is alerting available?
Ans: Yes, SMTP email alerts with cooldown and env-based controls.

Q8) What is future scope?
Ans: richer features, adaptive thresholds, periodic retraining, and stronger production security controls.
